Last month, Linux creator Linus Torvalds caused a bit of a stir when he posted this little nugget of sardonicism to a {{% link kernel-docs-remove-assisted-by %}}kernel.org mailing list thread{{% /link %}}:

> I don't understand this whole idiotic concept of "don't use AI for X".
>
> Here's a new rule just for you: don't use compilers for any of your kernel submissions.
>
> Because if you can't show that you really understand what the machine is actually doing by writing your code in assembler, then I don't want to see your code contribution. You clearly aren't competent if you can't write it that way.
>
> And btw, you had better not use an editor to write that commit message either.
>
> Because I need you to show me that you can actually write a good commit message without using tools that make it easy to backspace and hide the mistakes you made while typing.
>
> Ok?
>
> Because otherwise those tool-assisted commits of yours clearly aren't showing that you know what you are doing.
>
> Do you not see how UTTERLY STUPID those kinds of rules would be?

Torvalds was pushing back on a change proposed by Laurent Pinchart, who wanted to remove Assisted-by: references from commit messages that accompany code contributed to the project. The original thinking was that by removing the little hints AI coding agents leave in the changes they propose, it would steer the community's expectations a bit more toward human-written commits instead.

Torvalds argued that AI is a tool, same as a compiler or a text editor, and that setting a blanket expectation that its use is unwelcome is "utterly stupid" (de-emphasis mine). His position essentially boils down to the belief that the final artifact should speak for itself, and the tools and techniques involved in getting to that end state are inconsequential.

Imagine for a moment that we were asked to bulk-rename a variable across dozens of source code files. We could do it entirely by hand, retyping the new variable name into each location that needs to be updated. Perhaps there'd be some kind of zen-like quality to it, but that probably wouldn't be anyone's first choice. "Find/Replace All" is a more sensible tool for the task. A more involved version of this could introduce a script with a Language Server--level understanding of the syntax of the code. And yes, even asking an AI agent to make the change is yet another way to do it. {{% margin-note %}}For me, the sensible approach is somewhere in the middle. Doing it purely by hand is a misapplication of human effort, and using a long-running AI agent for such a straightforward task is an almost comically offensive waste of power and cooling.{{% /margin-note %}} The end result is the same in every case---the variable name in the code has changed. To Torvalds, the specific way we got there is inconsequential---only the end result matters.

The thing is, his argument isn't even wrong; he made a perfectly valid and totally defensible point. But he did so in a way that is going to embolden the worst people in our miserable zeitgeist: those with bad reading comprehension, bad brains, or both.

## There's too much confusion

In {{% internal-link you-dont-have-to %}}an earlier essay{{% /internal-link %}} I used a ship metaphor. {{% margin-note %}}In that same article, I also stated that this metaphorical ship had struck an iceberg and has been slowly flooding, bottom-to-top, for essentially the entire time it has existed. To those who view the world this way, "code" at any layer is an implementation detail that they need not concern themselves with. AI writes the code, AI tests and reviews the code, and to whatever extent a human is invited into this loop, the process is all but guaranteed to devolve into thoughtless "{{% link youtube-lgtm %}}LGTM{{% /link %}}"{{% margin-note side %}}I have sat for some time pondering the irony of an AI-generated song and music video criticizing the current state of AI development. When Torvalds facetiously says "don't use AI" the same way he facetiously says "don't use a compiler," he is (perhaps) unwittingly setting up an association in these people's minds that "AI is the new compiler, and one of the top authorities on the matter said so." This false equivalence is misleading to the point of almost being _"utterly stupid,"_ and it gives a blank check to people who seem to have turned rejection of critical thought into their entire philosophy for navigating life.

Torvalds works on projects that are primarily written in the C programming language, so it's reasonable to think that when he talks about compilers in a vacuum, he's thinking broadly about C. The essential function of a C compiler{{% margin-note side %}}And preprocessor, for the irritating pedants out there.{{% /margin-note %}} is to take the source code in a C file, along with the contents of additional files encountered in `#include` and {{% link cppreference-embed %}}`#embed`{{% /link %}} directives, and produce an object file---something that can _almost_ but _not quite_ execute directly on the target system's CPU. This clump of C source files and the resulting object file is called, conveniently enough, a **translation unit**.

The job of the compiler is fundamentally to _translate_ C code to object code. Every `if`/`for`/`while` in the C code is converted to an equivalent sequence of operations and conditional branching instructions. Each function call is faithfully preserved by pushing arguments onto the stack, or moving them into whichever processor registers the system's calling conventions dictate, and then emitting an appropriate `call` or branch instruction. There is sufficient correspondence between the C code and the resulting machine instructions that tools like Matt Godbolt's {{% link godbolt /%}} can meaningfully synchronize the highlighting from the C side to the assembly side and vice-versa.

Compilers preserve **semantics**---that is, what the program text _means_ rather than precisely what it says. An English-language demonstration might involve something like the following example sentences:

- "I went to the park."
- "The park is where I went."
- "I. The park. The former went to the latter."

Each of these sentences means pretty much the same thing, but they show significant differences when compared word-by-word. The subjects, verbs, and tenses are all consistent. Some take up more space, others are easier to read and quicker to extract meaning from, but they all carry basically the same semantic meanings. {{% margin-note %}}The differences? One might call them _style._{{% /margin-note %}} A compiler's job is to pick one of these representations in a way that doesn't change the meaning of what is trying to be said: There is a park somewhere, and at some point in the past I went there.

The simplest compilers could do a perfectly adequate job by blindly translating from one form to another. Take some C expression, emit a canned series of machine instructions, done---kind of like a fancy form of macro expansion. There's a small wrinkle in that, though: If the compiler just performs straightforward expression-at-a-time translation, the resulting program won't run very fast and will probably waste space.

Suppose I'm sitting on a couch with a friend, and they ask me when Richard Kind's birthday is. I don't know that, so I have to get up, go to the other room, dust off my leather-bound copy of _Oddly Specific Film Facts_, find the answer, put the book back on the shelf, and report back with my findings. Then they immediately ask me what year _National Lampoon's Christmas Vacation 2: Cousin Eddie's Island Adventure_ came out. I have to turn around, open the same book again, and re-do most of the work I already did. If I had known ahead of time that I would've needed both of those pieces of information, I could have combined the work of looking them up such that I'd only have needed one trip into the other room.

What about this head-scratcher of a text message: "I need you to stop at the grocery store on your way home from the park. If they have milk, pick up a rotisserie chicken. If they don't have milk, pick up a rotisserie chicken." {{% margin-note %}}You might ask what kind of person would conjure up such boneheadedly illogical and impossible conditions. Let me introduce you to {{% link imperialviolet-applebug %}}a spunky little upstart called Apple{{% /link %}}. Why the compiler didn't grab that engineer by the collar and slap them in the face with a flashing yellow warning message, who can really say.{{% /margin-note %}} The astute will notice that I don't have to check the store's milk supply at all---I'm bringing chicken home either way.

These types of scenarios are what **optimizing compilers** were made for. These heinously clever things exist to combine operations, tailor the instruction sequence to play to a particular target system's strengths, and to filter out things that it can prove will never logically occur.

Some optimizations are surprising. For example, a function call might be replaced by the body of that function if the compiler thinks the space used by the duplicated code is worth saving the execution overhead of a true function call. A `for` loop that runs a small but fixed number of times might be replaced by that many copies of the loop body based on a similar heuristic. Even in the 1980s, the Borland C compiler{{% margin-note side %}}Something that I learned a {{% internal-link "projects/cosmore" %}}whole hell{{% /internal-link %}} of a {{% link cosmodoc %}}lot about{{% /link %}}.{{% /margin-note %}} knew that it was faster to `pop` one or two values off the stack when cleaning up after a function call than it was to `add` an immediate value to the stack pointer register.

By the same token, calculating "9 divided by 5" using integer math is evidently slower on modern x86 processors than {{% link stackoverflow-multiplication-by-a-strange-number %}}multiplying 9 by -3,689,348,814,741,910,323, keeping the highest 64 bits of the result and then shifting that result two places to the right{{% /link %}}.{{% margin-note side %}}We're _still_ coming up with {{% link benjoffe-fast-floordiv %}}tricks{{% /link %}} for doing this class of operation.{{% /margin-note %}} Such instruction sequences might seem inscrutable, but this is a perfectly correct method for doing that particular division.

People like to harp on modern compilers for being "non-deterministic" in their outputs, but that's not really a fair criticism. Compilers work very hard---and their developers consider it a defect{{% margin-note side %}}{{% link appledev-linker-nondeterminism %}}Apple{{% /link %}}, {{% link llvm-nondeterminism-1 %}}LLVM{{% /link %}}, {{% link gcc-non-deterministic-dwarf-debug-info %}}GCC{{% /link %}}, {{% link llvm-nondeterminism-2 %}}LLVM again{{% /link %}}.{{% /margin-note %}} if they fail---to produce the exact same output for any given input. Two inputs that are byte-for-byte identical, using the same compiler with the same options, should produce byte-for-byte identical output programs. It's not that hard to find cases where this doesn't happen in practice, throw your hands up and say "what can you do, compilers are non-deterministic," but the actual fault almost certainly lies in the build processes that invoke the compiler. Build tools and the **continuous integration** (CI) systems that invoke them are complicated animals, and somebody's well-intentioned thought of "we should put the job number into this file so we can track which log files are associated with it" introduces a source of non-determinism into the compiler's inputs. These are things that the **{{% link reproducible-builds /%}}** project works on, to varying degrees of industry indifference.

The key thing to remember here is that one of the compiler's core tenets is to preserve the exact semantics of the input code, and to avoid emitting optimizations that it can't prove are safe _with mathematical rigor_.

## None of them along the line know what any of it is worth

This brings us to **large language models** (LLMs) and some of their differences. Anybody can go to ChatGPT right now, type "eggs" into the text box, and press Enter. It will generally respond in a kind of "What exactly do you want to know about eggs?" hint response of maybe fifty words. {{% margin-note %}}It goes without saying, but I will say it anyway: I had to run the test multiple times because the LLM's output was not deterministic. Like, _at all._{{% /margin-note %}} I tried this a few times, and the response is, on average, 80&times; the character count of the prompt.

In a different request, one could feed an LLM their 60,000-word master's thesis on egg sciences and prompt for a response that boils down to a single yes or no. There is no inherent preservation of structure or semantics between the input and the output. A naked LLM simply does not offer such a guarantee.

Each of these two users believes that they're using the model correctly. The interaction with the first person feels like a fun interactive adventure game, when in reality the model is furiously hunting around for any additional information that would make one line of response more statistically plausible than all others. In the second interaction, the model might have silently lost context on the first forty pages and nobody would have any way to know without interrogating it for a specific fact from that part of the text.

Put these two people in a room (or a Hacker News thread) together, and they will each independently say "Oh yeah, worked great, gave me exactly what I needed, saved me time." But there tends not to be a lot of detail shared about the exact techniques employed. Reading anecdotal stories about different experiences with the technology, it's typically not clear which users prompted the model with everything they had ever learned and which ones said "eggs." The output, taken on its own, gives no clues about the nature of the input that brought it into being.

We can steer this back around to Torvalds's comment and see how his lack of precision about _who exactly he is talking to_ can be so dangerous.

The people who contribute code to the {{% link kernel-org %}}Linux Kernel Organization{{% /link %}} are hardcore experts on Linux internals and the system software that underpins a substantial portion of the internet along with many, many mobile and embedded devices. These are people with loads of experience who know more about the guts of this stuff than I feel I could reasonably learn in a lifetime of study. I have a fair amount of trust that these types of contributors would guide their AI-assisted development by feeding their full knowledge of a system into the model's context, prompting for a very specific and pointed answer, and taking from it small and tightly-scoped fragments of code. I believe they would carefully consider and tweak the result before submitting it back to the project. And I'd like to think, above all, that they would deeply understand the changes, the motivations behind the work, and if necessary the lines of debate for defending their choices. {{% margin-note %}}I would like to think these things, but {{% link cve-tls-handling-dos-flaw %}}day{{% /link %}} after {{% link copy-fail %}}day{{% /link %}} after {{% link cve-kernel-ipv4 %}}day{{% /link %}} my faith is shaken to its core. So I don't even know anymore.{{% /margin-note %}} These are the kinds of people Torvalds was talking to, and about.

Most software engineers are not Linux kernel contributors. Not even close. Most developers don't work in C, and {{% link tiobe-index-python %}}a plurality of us{{% /link %}} don't even have to compile the code we write at all. We don't generally need to worry about allocating and freeing memory, handling interrupts, or satisfying the flow control requirements of some awful peripheral device with even worse documentation. We work on a layer that is so far insulated from the true nature of the machine that we get to pretend that the whole mess of complexity underfoot isn't actually there.

But here's the thing: _Nobody_ actually operates at a level where they are in complete, absolute control of how the job gets done. The Python programmer doesn't have a say in whether {{% link lwn-python-tail-calls %}}tail calls{{% /link %}} are used by the interpreter or not. The C programmer doesn't get much of a vote on how the compiler allocates registers. The assembly programmer can't tell the CPU's microcode what to do with regard to speculative/out-of-order execution, prefetching, cache behavior, or how the MMU might spray a program's variables across the physical memory chips in the system. Even the simplest intuitions like "_X_ clock cycles to perform an operation, _Y_ clock cycles per second" are dead and buried and have been ever since we started actually caring about how long we could run software off a battery. Assembly programming today is all about communicating enough intent to the hardware so that it can make optimal decisions about execution, rather than micromanaging the state of every logic gate.{{% margin-note side %}}{{% link gigatron %}}The option is still available{{% /link %}} if you want it, though.{{% /margin-note %}}

If you're looking for a reason to lay awake tonight staring at the ceiling, consider that there is very little in our lives that we can assert complete control over. When I drop a package off at The UPS Store, I don't get to tell the workers exactly how to route the shipment and orchestrate its delivery. When I step on the accelerator pedal on the drive home, I don't get to dictate how many microliters of gasoline are injected into each cylinder, same as how the operator of an electric vehicle can't specify the frequency or shape of the AC waveform going to the drive motors. As important as I feel it is to tell everybody working in food service "Hey, make sure there are no spiders on that head of romaine before you run it through the shredder," I can't force anybody to do that; I can only trust that they did so as part of our mutual agreement to perform the work.

"I need this to be delivered to Boulder by Friday." "This vehicle must move forward on command." "I want to bite into this burrito and not experience an inappropriate sort of crunch." These are **contracts**---given this input, require this output. They clearly and rigidly define the boundaries between what I care about and what the other party cares about. If I don't specify a detail, that detail becomes immaterial to my side of the interaction. This happens all the time across every facet of life, and is fundamental to the business of getting any kind of coordinated work done at all.

It turns out I don't actually care if my package travels by air or by truck. I don't want to have to think about how fuel atomizes differently when it's cold. And as much as the thought makes my skin crawl, I'm sure I've ingested a spider during some meal at some point in my life and didn't even notice. I delegated all of those decisions to somebody or something else, but those decisions were still made.

Just because a person decides not to engage with them, it doesn't make the decisions go away.

## No reason to get excited

If we were to accept the premise that LLMs are functionally similar to compilers, a representative fragment of input might look something like:

> An expression that evaluates to the value of `a` if `a` is larger than `b`, otherwise `b`.

The Python code for this would be `a if a > b else b`, while in C it would be a bit tighter: `a > b ? a : b`. This is what compilation is all about---high-level to lower-level, and with some loss of fidelity the operation can even be reversed to get a semantic equivalent of the original input back.

There's even some wiggle room in the conversion. The input didn't specifically dictate:

> An expression, **and not a function call or macro,** that evaluates to the value of `a` if `a` is larger than `b`, otherwise `b`.

Without that added detail, our compiler would be well within its rights to instead emit a call to `max(a, b)` in Python or `fmax(a, b)` in C if it felt the optimization was appropriate in the broader context of the program. If the author didn't specify, they waive their opportunity to have a voice in the matter.

One might take a step back and notice that this is an _"utterly stupid"_ way to use an LLM to write code. Typing this sort of input in natural language is verbose to the point of almost tedium---longer to write, harder to skim, and for no real benefit to anybody. The more sensible approach would be to go one step higher and ask, _why_ do I care whether `a` or `b` is larger? Could `a` and `b` relate, in the real world, to the width and height of a 4&times;6-inch photograph that I'm trying to fit into a 4&frac18;&times;9&frac12;-inch envelope? It will fit, but only in one orientation!

So maybe I ask:

> A function that takes the dimensions of a rectangular object and an enclosure. Returns true if the object can be rotated to fit entirely inside the enclosure.

Maybe this would emit code that uses a ternary operator, or a function that computes maximums, or `(a1 < a2 && b1 < b2) || (a1 < b2 && b1 < a2)`, or some ridiculous 256-bit AVX2 monstrosity. Doesn't much matter to me---I want to shove four numbers into the mystery box and get a boolean answer out of it.

But if we're doing that, why are we even thinking of functions at all? There must be some higher reason why we're engaging with this task in the first place, so let's operate at that level instead:

> A price estimator for a print-on-demand photo website that calculates the total postage necessary to ship all items in the user's shopping cart.

Ah, now we're vibin'! Will we actually require the enclosure-testing function we just described? Or would this be a lookup table pre-populated with postal rates for every size package we stock? What kind of database would that data be stored in, assuming it existed? Where did the rate table even come from? Will the UI for this part of the site be rendered in Geist Mono or JetBrains Mono?{{% margin-note side %}}We get it, Claude---the only way you can reliably figure out if a piece of text is going to fit inside a certain area of the screen is to literally count the characters. Only took you {{% link cnbc-anthropic-ipo %}}$1.8 trillion{{% /link %}}.{{% /margin-note %}} We didn't specify! Did the original input to this process actually contain a single, directly actionable decision?

> Please produce a program that reads the RSS feed at `https://www.scottsmitelli.com/articles/index.xml` and prints a list of all post titles.

I gave this prompt to Google Gemini, received the following response from their 3.5 Flash-Lite model:

```python
# ScottSmitelli.com Note: This code block was produced by AI.

import urllib.request
import xml.etree.ElementTree as ET


def fetch_rss_titles(url):
  # Set a basic User-Agent to avoid being blocked by some servers
  req = urllib.request.Request(
      url, headers={"User-Agent": "RSS-Title-Fetcher/1.0"}
  )

  try:
    print(f"Fetching feed from {url}...\n")
    with urllib.request.urlopen(req) as response:
      xml_data = response.read()

    # Parse the XML content
    root = ET.fromstring(xml_data)
    titles = []

    # 1. Check for standard RSS feed items (<item><title>)
    for item in root.findall(".//item"):
      title_elem = item.find("title")
      if (
          title_elem is not None
          and title_elem.text
          and title_elem.text.strip()
      ):
        titles.append(title_elem.text.strip())

    # 2. Check for Atom feed entries (<entry><title>), handling namespaces
    for entry in root.findall(".//{*}entry"):
      title_elem = entry.find("{*}title")
      if (
          title_elem is not None
          and title_elem.text
          and title_elem.text.strip()
      ):
        # Prevent duplicates if RSS/Atom fallback overlaps
        clean_title = title_elem.text.strip()
        if clean_title not in titles:
          titles.append(clean_title)

    # Display the results
    if titles:
      print(f"Successfully found {len(titles)} post titles:\n")
      for index, title in enumerate(titles, start=1):
        print(f"{index}. {title}")
    else:
      print(
          "No titles found. The feed structure might be formatted"
          " unexpectedly."
      )

  except Exception as e:
    print(f"Error fetching or parsing the feed: {e}")


if __name__ == "__main__":
  feed_url = "https://www.scottsmitelli.com/articles/index.xml"
  fetch_rss_titles(feed_url)
```

So, just to get the obvious out of the way, this one-shot program works and adheres perfectly to the prompt. I quite literally got what I asked for.

This program has a cyclomatic complexity{{% margin-note side %}}Measured via `radon cc`, and my gut says this number feels about right.{{% /margin-note %}} of 13. You can ask whichever GPT-6 model that picks up the call to "Write me an example of a non-trivial computer program" and it will spit out a Task Management System written in Python.{{% margin-note side %}}This appears to be something that OpenAI specifically coached their model to do, as it reliably emits this specific program in response to this request.{{% /margin-note %}} Why'd it pick that? Simple: Because I didn't.

Mash button, receive treat. LGTM.

It should go without saying, but the decisions made by these models are universally _ass._ It's blatantly apparent in AI writing, imagery, narration, code, everything---the fundamental ingredient in any work of slop is a conspicuous absence of human volition.

We seem to be in a kind of "good enough" stage of history right now. And not necessarily because "good enough" is actually good enough, but more because "good enough" was just about the only thing we could collectively muster. Things look right if we don't stare too long, they sound right if we don't listen too hard, and they work right as long as we don't actually try to use those two-factor recovery codes. Half-baked prototypes pushed to production without adequate care then ultimately abandoned. This unyielding march of progress, not because the progress itself is valuable, but because progress is the only thing we've ever known that felt like success. Past performance does not guarantee future results.

Vibe coders, boosters, and accelerationists, do these people even _like_ computers? I'm tired of the "good enough" era and I'm tired of the people I'm forced to live through it with.

## There are many here among us who feel that life is but a joke

Something else has been bugging me lately: the whole Roko's Basilisk thing I brought up earlier. If you're unaware of it, the essential idea is that we're supposed to believe that humanity will inevitably create an all-knowing and all-seeing super-intelligence which will be able to look back over historical records and determine who did and who did not assist with its creation. The people who did _not_ help, but could have---and who are now in all likelihood deceased---will be "brought back" via simulation inside the super-intelligence, and that simulated version of the person will be tortured, presumably forever, for their past transgressions. This is meant to incentivize every able-minded person to build this super-intelligence via a mechanism that is basically blackmail.

Mere awareness of this idea is supposedly sufficient to earn a person a spot on the super-intelligence's shit list, because now everybody who read the preceding paragraph is aware that the super-intelligence is coming. It's coming _for you._ When this concept first circulated on the LessWrong forums in the early 2010s, people were becoming so distraught by the idea that the site's owner banned discussions on the topic for years. {{% margin-note %}}I'm not bothering to link to any of this, because the people and websites involved are just awful. It was how {{% link vice-rokos-basilisk-elon-musk-grimes %}}Elon Musk got together with Grimes{{% /link %}}, after all.{{% /margin-note %}}

If this sounds like a spectacularly dumb thing to spend any appreciable amount of one's finite time on this earth worrying about, I guarantee that a _distressing_ number of people working at the frontier AI labs have pondered and discussed this a whole lot longer. This is essentially Pascal's Wager for people who believe they are going to invent Silicon God. Many "serious" thinkers have given this idea a substantial amount of "serious" thought and have formed many "serious" opinions that have been painstakingly laid out in blog posts that make this one look like a bathroom limerick in comparison.

There is a rebuttal to this whole idea in "{{% link hexmhell-galileos-basilisk %}}Galileo's Basilisk{{% /link %}}" by hex_m_hell, which remains one of the finest pieces of writing on the subject that I've yet encountered. I will not make any further attempt to poorly restate their points, but I encourage anybody who's slightly suspicious of this idea to at least give the post a look.

For whatever it's worth, I look at it like this: Suppose there is a button you can push that instantaneously generates a complete duplicate of me. Same body, same memories, same thoughts, a complete copy down to the subatomic level. The only difference is that the clone has "Scott 2" written on his forehead in Sharpie. Trippy? Yes. A violation of most if not every law of nature and physics? Certainly. You then take Scott 2 and throw him directly into a wood chipper. Once I shake off the initial shock and horror of the scene, I believe I would have two main things to say in response: 1) "I don't know who that guy was, but _he wasn't me._" 2) "We should leave before the cops come."

Anyway, I'm really bothered by the caliber of the people we have helming this ship. The notion that I should be surrendering _both_ my decision-making _and_ my money to them is simply obnoxious to me.

## So let us not talk falsely now

It wasn't all that long ago, back when token usage leaderboards roamed the earth, that we all collectively discovered that pitting employees against one another in mandatory AI pissing contests was not a smart business strategy. Every executive who pushed for something like that was, on some level, demonstrating bad judgment and terrible leadership. Anybody who is _still_ championing token usage leaderboards today is not just a terrible leader but also a dickwit.{{% margin-note side %}}Feel free to tell them I said that.{{% /margin-note %}} But if all that tokenmaxxing for its own sake was so clearly misguided, it doesn't take much limberness in logic to conclude that requirements _against_ generative AI use---blanket bans, sternly-worded policies, finger-pointing at code because it has a bit too much of that LLM smell---aren't unassailable either. The parties mandating _or_ prohibiting AI use are doing so because it's a single clearly-defined thing they can grunt toward without leaving any viable avenues for criticism or nuanced debate. They make everything about AI because it's easier than trying to articulate far murkier aspects of human interaction, and they never bothered to try to refine their positions because, I suppose, they suck.

It feels weird to say for some reason, but I agree with Linus Torvalds. Blanket policies that dictate a person **_must_** or **_must not_** use AI for a given task are unhelpful, divisive, and lead to debates that never go anywhere because the thing being debated isn't even what's important. AI usage isn't the problem. AI is an amorphous glob that creeps into every crack and corner of an idea where somebody gave up on the work of making a choice. Its effects, its impacts, its _voice_ are only as strong as the deficiencies of the person wielding it.

As for that RSS parser from earlier in the article, here's how I would've written it:

```python
#!/usr/bin/env -S uv run --script
# /// script
# dependencies = ["requests"]
# ///

import requests
from xml.etree import ElementTree

resp = requests.get("https://www.scottsmitelli.com/articles/index.xml")
rss = ElementTree.fromstring(resp.content)
for t in rss.findall(".//item/title"):
    print(t.text)
```

I understood better than any agent what this code was _for_: It was a throwaway program to be executed once as a demonstration that there is really only one path through the task that is worth considering. I had to look up how to use `ElementTree` and the methods it exposes because I do not currently inhabit whichever circle of Hell involves parsing XML with any regularity. I used the `requests` library because _of course I did._ I copy-pasted the `uv run` incantation from a different script I had written earlier because laziness is a goddamn virtue. I didn't do anything I didn't strictly need to do, including handling errors.{{% margin-note side %}}Because in this specific demonstration, I knew the error would not happen. And if somehow it did, I knew the unhandled error would not matter.{{% /margin-note %}} And yet, I didn't _strictly need_ to create the `resp` and `rss` variables---that was done for human readability. I picked `resp` in this case instead of my usual `res` because I knew my decaying eyeballs would conflate `res` and `rss` should I ever decide to read this code again. {{% margin-note %}}One of the core benefits in using a high-level language is the opportunity to make these naming choices rather than trying to remember what's in `qword ptr [rbp-16]`.{{% /margin-note %}} I can detect a certain voice in his artifact, terse as it is. If I randomly stumbled across it in five years without the surrounding context, I think I might be able to identify it as something I would have written simply by the way it looks as a whole. How insufferably pretentious of me.

Maybe I'm simply too dumb to operate a computer in 2026, but I do not know how to instruct a coding agent to carry out this task in so little _readable_ code without resorting to prompts and guardrails that are longer and more unpleasant to create than the output is. And without that massive prompt, well, you saw what it did earlier.

I do believe that Torvalds has done real damage here by putting AI tools on the same playing field as compilers, because they are fundamentally not the same. You can make an LLM _behave_ like anything you want---including a compiler---but that doesn't make it one. Patrick Stewart wasn't actually a starship captain, you know? {{% margin-note %}}Although he _has_ {{% link youtube-ive-seen-everything %}}seen everything{{% /link %}}.{{% /margin-note %}}

The admonition in Torvalds's message should have been "You had better not... what?" Skip whichever steps of this abstract task we all arbitrarily agreed were important? Sign your name to work you didn't do? Be an idiot? Where is this squishy boundary between machine-translating one carefully considered expression of an idea into a different form, versus delegating the entire responsibility to something that adheres to no beliefs, learns no lessons, and feels no shame? I have no idea. It's not really something that can easily be spelled out in black and white. And everyone who tries just makes themselves look dumb in the process. {{% margin-note %}}And I am including myself in this group.{{% /margin-note %}}

Unfortunately, it appears that our environment is turning us into spineless cowards, eager to farm out even the smallest of decisions to an entity that is ultimately incapable of experiencing the consequences of choosing badly. And I understand the appeal---decisions are annoying, exhausting, uncomfortable, and at times even gut-wrenching. As unpleasant as they are, they still need to be made. Of course we'd want to grasp for anything to make that easier. LLMs, agents, and all other forms of generative AI simply provide a low-friction way to weasel out of that duty, and evidently some of us are quite willing and eager to pay for the privilege.

And that, to me, is _"utterly stupid."_
